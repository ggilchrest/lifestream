Local fixture testing

Lifestream human testing guide

Use this guide to exercise the features a person can see and operate in the local Assistant application. Check the expected result after each action and record any mismatch with the exact step, visible message, and screenshot.

Scope boundary: this environment uses fixture authentication and fixture providers. A passing checklist proves the local user journey only. It does not prove production sign-in, physical microphone quality, acoustic quality, learned behavior, real training, deployment, or production readiness.

1. Start the test environment

1
From the repository root, build and start the local server.
pnpm build
LIFESTREAM_PROFILE=test PORT=3137 node apps/server/dist/index.js
2
Open Assistant control. Use Conversation for typed and voice tests. The permissions page is available at Review permissions.
  • The control page loads and shows Development mode.
  • The notice says fixture administration and explains that real sign-in is not configured.
  • The health indicator becomes Ready.

2. Create and manage an Assistant

  • Click New Assistant. An Assistant appears in the rail and the editor shows a draft.
  • Change the display name and identity statement; click Save revision. A new revision appears in History.
  • Click Preview draft. Confirm the result says preview only and that no revision is saved or activated.
  • Click Activate revision. Confirm the status changes to active.
  • Click Export. Confirm a JSON download is produced.
  • Use Import definition with a safe exported definition. Confirm it creates a preview/draft path, not an automatic activation.
  • Create another revision, activate it, then use Rollback latest or the revision rollback controls. Confirm rollback creates a reviewable draft.

Expected boundary: drafts and previews never silently change the active Assistant.

4. Exercise the relationship journey

Complete these actions in order for the selected Assistant. Use synthetic text such as “Prefers concise explanations.”

  1. Under People & Context, click Start relationship review. A relationship appears.
  2. Click Add candidate. Confirm each candidate visibly includes Status, Uncertainty, Source, and Source Family.
  3. Approve one candidate and reject another. Confirm the status and revision update; stale submissions must be rejected.
  4. Use Skip bootstrap and confirm ordinary Assistant use remains available.
  5. Under Working Controls, choose Balanced, Concise, or Coaching. Move several sliders and click Save draft.
  6. Click Inspect effective context. Confirm included, omitted, source-revision counts and limitations are shown.
  7. Click Activate latest draft. Confirm activation is explicit. Try Reset to known good and Rollback latest; each should create a reviewable draft.
  8. Click Inspect prepared request. Confirm a prepared-context manifest is shown and hidden reasoning/private prompt text is not exposed.

5. Insights and feedback

  • Click Run insight lenses. Confirm five lenses render: evidence quality, communication fit, context use, structure/compression, and training opportunity.
  • Inspect uncertainty, support, counterevidence, intervention, benefit, cost, risk, validation, and inverse fields.
  • Click Record explicit feedback for a candidate. Try reaffirmation, correction, helpfulness, style, and salience.
  • Accept or reject an insight proposal. Confirm active relationship state does not change directly.

Expected boundary: retrieval, repetition, style, and salience feedback must not silently become factual evidence.

6. Relationship Lab

  • Click Prepare Lab. Confirm two representations, bounded scenarios, declared criteria, held-out scenarios, and repeated runs.
  • Click Run comparison. Confirm isolated results, variability, held-out exclusion, and limitations render.
  • Click Promote for normal review or reject it.
  • Refresh the relationship and confirm promotion/rejection did not directly activate relationship state.

Expected boundary: the Lab is synthetic and isolated. It cannot write live memory, send notifications, activate itself, or prove learned quality.

7. Typed conversation

Open Conversation. Keep the browser tab on localhost so microphone permissions and fixture authentication work.

  • Confirm the backend/profile status and provider identities are visible.
  • Send a short typed message. Confirm the user message and Assistant response render in order.
  • Click Stop response while a response is generating. Confirm the request stops visibly and the next message still works.
  • Try an empty message or malformed control input. Confirm it is rejected with a visible error and no false completion.
  • If a relationship is selected by the page flow, confirm the prepared relationship context is present in the request boundary; do not treat inclusion as proof of causation.

8. Voice, speech, and interruption controls

These steps require a browser with microphone access. Use headphones where possible and do not use private recordings.

  • In Voice settings, choose a tone/preset, seed, pace, and energy. Click Apply settings and confirm the status says they apply to the next session.
  • Click Speaker test. Confirm audio or a truthful failure message is visible.
  • Click TTS test with the default short text. Confirm ordered playback and a terminal result.
  • Click STT test. Confirm the transcript or a truthful unavailable/error state.
  • Click Start microphone and grant permission. Confirm capture state, level meter, device information, and reported browser audio settings.
  • Speak a short sentence, pause, and confirm committed speech appears as a user transcript followed by an Assistant response.
  • Click Mute microphone, speak, then unmute. Confirm capture state changes and muted input does not create a false turn.
  • Speak while the Assistant is responding. Confirm barge-in interrupts playback/generation once and the UI reports the interruption.
  • Click Stop capture. Confirm audio tracks close, capture stops, and a new session can be started.
  • Optionally choose a 2–20 second single-speaker reference clip only if you have permission. Confirm the explicit consent checkbox is required; cancel or clear it and verify no clip is sent.

Do not interpret fixture audio as proof of physical audibility, acoustic echo cancellation, speaker identity, real-provider parity, or production latency.

9. Permission and isolation checks

  • Open Review permissions. Confirm the page identifies fixture authority and does not imply production sign-in.
  • Open a second private window or use a different fixture principal if available. Attempt to view another Assistant or relationship.
  • Confirm the request is denied or returns a non-disclosing not-found result.
  • Reload the control page and confirm the selected Assistant and accepted relationship/configuration state remain available.

10. What to report

For each failed or surprising step, report:

  • Section and step number.
  • URL and selected Assistant.
  • Exact visible text or error.
  • What you expected and what happened.
  • Screenshot, if layout or state is involved.
  • Whether the failure was fixture behavior, browser permission, provider availability, or an application defect.

A concise acceptance statement can name the tested scope, for example: “I accept the S080 forgetting/recovery workflow and the S081 joined relationship journey as observed in the local fixture environment.”

Guide scope: local fixture-facing features currently served by the control and conversation surfaces. Human acceptance, fixture verification, real-provider evidence, perceptual evidence, performance evidence, and production acceptance remain separate claims.
