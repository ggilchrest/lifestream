# Canonical authority and capability messages

`@lifestream/contracts/provider-messages` exports types generated from the published JSON Schemas. Run `node scripts/generate-provider-types.mjs` after an authorized schema change, or use `--check` to detect drift. Generated types describe structure; format, size, conditional and cross-message constraints require runtime checks.

`@lifestream/runtime/ports/provider-messages` declares all four AuthorityProvider methods and all four CapabilityProvider methods. Wrap an implementation with `CanonicalProviderBoundary` from `@lifestream/runtime/ports/provider-boundary` before exposing it to a runtime consumer. This component has isolated conformance coverage. Canonical grant HTTP administration is now integrated as described below; the existing capability resolver, control-web grant workflow and PWCE action mapping still need migration to these envelopes.

The trusted composition root supplies the configured provider identity, cancellation signal, current-scope predicate and a finite maximum duration (30 seconds by default). Local Human decisions and nonempty grant lists also require the authenticated principal ID. Every incoming and outgoing object is copied, checked against its exact operation schema and frozen. The boundary rejects non-JSON values, custom objects, accessors, cycles, excessive nesting, more than 8,192 visited values or more than 1 MiB of JSON. Wire decoders must separately reject duplicate JSON keys before producing an object.

Effects require explicit host admission callbacks. `admitInvocation` must verify the current catalog and scope, resolve and validate the pinned input schema, and check the trusted dispatch receipt. A null receipt is acceptable only for a currently verified non-effectful, unprotected operation. `admitDispatch` must verify the governing provider and its evidence against current authenticated authority state. Callback approval is not a wire field; never derive it from a client boolean or from the presence of an artifact reference. These callbacks do not replace the provider's durable serialization, one-use consumption or idempotency records.

The boundary checks invocation/input/operation identity before invoking either callback, fences completion after each await, and preserves canonical result discriminators. `outcome.status=succeeded` may contain a denied decision, an intermediate capability status, or an unknown effect. Only a confirmed capability `succeeded` payload contains output. Metadata validation checks the shape of schema and evidence references; the consuming resolver must still resolve authorized immutable bytes and validate the output against its original schema. It must never fetch a URL merely because it appears in a reference.

A local exception after entry to `invoke` or `authorizeDispatch` sets `ProviderBoundaryError.effectMayHaveStarted=true`. Preserve the original invocation and idempotency key for reconciliation. The boundary does not retry, claim rollback, issue grants or synthesize receipts. A thrown provider error has a safe local code without the provider's raw message.

Invalidation subscriptions use sequence zero for each new stream, including a resumed subscription; the request's prior sequence is a source cursor. The boundary enforces contiguous frame numbers, fixed identities, scoped data, an explicit terminal and EOF. It withholds the terminal until bounded EOF verification rejects extra frames. Data may already have been delivered when a subsequent frame fails, so a cache consumer must invalidate on stream error or an explicit gap and refresh before protected use. Consumer cancellation aborts the provider signal; an uncooperative iterator cleanup cannot delay return indefinitely.

This component does not certify durable idempotency, actual PWCE authority/action semantics, artifact-store contents, cold process recovery, selected-provider qualification, physical effects or Human acceptance. Those remain owner-specific integration obligations.

## Durable admission prerequisite

The existing authenticated tool route now records the principal, Assistant, session, capability, input digest and checked dispatch binding in the same SQLite transaction as admission, one-use consumption and audit. The binding includes endpoint/environment labels, capability version and complete definition digest, provider route, snapshot identity/revision, interaction, authority context, execution mode and original deadline. A later request cannot supply missing identity for a historical admission. Exact retries return the recorded admission; changed identity conflicts. The evidence accessor returns the actual recorded bytes with their digest and size under an explicit trusted current-owner check. This is internal evidence of the checks performed, not a reconstructed canonical HumanAuthorityDecision.

Before provider I/O, the server durably claims that original admission once. Two database owners or processes cannot claim it twice. Claiming rechecks grant ownership, revision, scope, session, expiry, mode, deadline and the caller's current guard. A stored claim survives restart and missing provider output; further use remains unknown and requires reconciliation. Audit or storage failure rolls back the corresponding transaction. Existing one-use grants are not recreated when a claim fails.

These changes repair the existing runtime path but do not complete canonical consumer migration. The administration endpoint still uses its existing internal endpoint/environment labels and coarse capability grant terms. The HTTP request layer now binds a required UUID idempotency key to one invocation before provider work, preserves verified responses across restart, rejects changed content and revalidates access before replay. Incomplete records stay uncertain without replacement dispatch. The local administration status resource can now reconcile an original invocation under its durable provider/scope/schema binding, append observations separately, and preserve the original HTTP reply. Full canonical request envelopes, authoritative effect-evidence references and final scope mapping remain outstanding. Historical backup restore fencing, real PWCE admission and action reconciliation also require their separate integration evidence.

## Canonical grant storage

`CanonicalGrantRepository` stores the published `GrantRequest`, `HumanAuthorityGrant` and `GrantLifecycleEvent` records in separate SQLite tables. Creating a request is inert. Approval compares the current request revision, confirmation digest and explicitly confirmed class and deadlines, then commits the terminal request, exactly one grant, issuance event and command response together. Competing approvals and denial serialize on that same database transaction. Recorded command retries return the original result, including after revocation; they do not revive permission. Callers must read current grant state for current eligibility.

The host supplies a current authenticated principal, governing provider, clock and scope guard. A trusted capability adapter supplies scope derived from validated arguments, the input digest and deterministic effect summary. The repository checks these bindings and exact schema shapes; it does not authenticate a caller, resolve authentication-evidence bytes or derive scope from raw capability arguments itself. When an adapter can provide only an input-bound scope, reusable session and persistent grants are rejected.

Request history and grant events retain their original bytes and SHA-256 digests. Expiry is enforced directly and can be materialized lazily; terminal grants never reactivate. Approval fails if the clock is invalid, predates the request, or crosses a request/grant/review deadline during final ownership checks. Records with mismatched digests or IDs and inconsistent event histories are withheld. Storage is bounded to 4,096 requests and 16,384 command results; it fails explicitly at capacity instead of evicting retry or approval history.

`evaluateCanonicalGrant` is a non-consuming eligibility function for one explicitly selected grant. It checks current Human/session/provider context, normal execution mode, endpoint/environment/Assistant identity, exact capability version and operation, target/data subsets, one-use invocation and input bindings, lifecycle state, and expiry/review boundaries. Empty data scope means no data access. Its result is an eligibility disposition, not a canonical decision artifact or dispatch receipt.

The focused tests use temporary databases, a virtual clock, synthetic identities and independent competing database workers. The canonical HTTP API below adds owned listings and authenticated audit custody. Control-web integration, final dispatch consumption/invalidation, and the actual capability adapters supplying host-owned scope remain outstanding. Existing coarse grants retain their original storage; this migration does not assign them missing canonical terms. The saved administration service has not been restarted or migrated by this work.


## Canonical grant HTTP administration

The local-password server now handles the nine published `/api/authority/v1` grant routes with the canonical request and response schemas: list/get/create requests, approve/deny/cancel a request, list/get grants, and revoke a grant. The current control-web grant screens still use the earlier Assistant-scoped endpoints; switching that workflow and the tool dispatcher remains separate work.

POST bodies are the published envelopes with request ID, correlation ID, idempotency key and typed payload. Path IDs must match payload IDs. GETs accept request/correlation ID headers and generate missing IDs. List queries use `assistantId`, comma-separated `states`, `limit` (default 50, maximum 100), and an opaque `cursor`. Unknown or duplicate query fields are rejected. Cursors bind the Human, Assistant, list/filter/limit and source revision; changing those or changing stored state requires a fresh page. Each page repeats current authentication and Assistant permission checks.

Canonical JSON decoding rejects invalid UTF-8, malformed JSON, duplicate keys including escaped spellings, more than 128 KiB, more than 8,192 structural/string tokens, or nesting beyond 32 levels. Contract validation rejects forged principal/state fields and invalid types. Cookie mutations retain the existing origin and CSRF checks. Direct grant creation, deletion, state replacement and dispatch admission have no canonical route. Errors use the canonical failure envelope with safe codes; another Human's IDs are not disclosed.

Creating a new request requires the trusted `ServerOptions.canonicalAuthority` composition input. It supplies an environment UUID, a current-scope guard and an asynchronous proposal resolver. The resolver must retrieve the original invocation and derive its material scope and input digest from validated arguments under the selected capability contract. Returning client fields unchanged is not such verification. The API compares every submitted display/authorization term with the trusted proposal and checks the current session's actual logical endpoint, environment and Human ownership again before commit. Missing composition stays unavailable for new creation/approval; it never derives authority from the request body. PWCE governance never falls back to this local provider.

Approval captures a credential-free local authentication proof and commits it with the request decision, grant, lifecycle event, immutable record snapshot, audit record and idempotency response. The provider-owned audit format `urn:lifestream:local-authority-audit:1` records operation, request/correlation IDs, Human/Assistant, command digest, disposition/revision, reason, event IDs and a digest-bound reference to the exact resulting canonical request/grant snapshot. `urn:lifestream:local-authentication-proof:1` records verified identity/session/origin and authentication/verification times; it contains no cookie, token hash, CSRF value, password or MFA material. These are local evidence formats, not new authority transport envelopes. Artifact references resolve to actual owned SQLite bytes; replay verifies the audit, linked snapshot and approval proof before returning success. An audit-write failure rolls back the whole approval.

An identical command returns its original recorded result without consulting a changed proposal source or creating another grant. Current authentication, Assistant permission and evidence access are still required. The returned decision may precede a later revocation; clients must refetch the current grant to display current eligibility. A changed command under the same key conflicts. Historical command results without the required audit custody are not upgraded by fabricating references.

Canonical GETs do not change stored request/grant state or create lifecycle events. They return the stored lifecycle record; grant views separately compute eligibility against current time, session, endpoint, host scope and proof custody. The request's explicit `expiresAt` remains authoritative even while its stored state is pending. Review/expiry boundaries deny permission immediately without requiring cleanup. Grant histories are bounded by the current finite lifecycle, and all current canonical grants have no admitted invocation because canonical dispatch is not yet connected. Integrating dispatch must supply its real admitted-invocation ledger and invalidations.

Validation uses real local-password HTTP sessions, temporary databases and a synthetic trusted proposal source. It covers all nine schemas/routes, atomic audit rollback, stale/forged terms, idempotency after revocation, cross-Human isolation, pagination, scope withdrawal during resolution, strict JSON decoding, read-only expiry views, evidence corruption and external-governance refusal. It does not establish the actual deployment/capability proposal adapter, canonical control-web UX, final dispatch, selected-provider qualification, physical effects or Human acceptance. No saved service was restarted or configured.
