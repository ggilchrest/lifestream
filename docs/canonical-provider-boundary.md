# Canonical authority and capability messages

`@lifestream/contracts/provider-messages` exports types generated from the published JSON Schemas. Run `node scripts/generate-provider-types.mjs` after an authorized schema change, or use `--check` to detect drift. Generated types describe structure; format, size, conditional and cross-message constraints require runtime checks.

`@lifestream/runtime/ports/provider-messages` declares all four AuthorityProvider methods and all four CapabilityProvider methods. Wrap an implementation with `CanonicalProviderBoundary` from `@lifestream/runtime/ports/provider-boundary` before exposing it to a runtime consumer. This component has isolated conformance coverage. Canonical grant HTTP administration is now integrated as described below; the existing capability resolver, control-web grant workflow and PWCE action mapping still need migration to these envelopes.

The trusted composition root supplies the configured provider identity, cancellation signal, current-scope predicate and a finite maximum duration (30 seconds by default). Local Human decisions and nonempty grant lists also require the authenticated principal ID. Every incoming and outgoing object is copied, checked against its exact operation schema and frozen. The boundary rejects non-JSON values, custom objects, accessors, cycles, excessive nesting, more than 8,192 visited values or more than 1 MiB of JSON. Wire decoders must separately reject duplicate JSON keys before producing an object.

Effects require explicit host admission callbacks. `admitInvocation` must verify the current catalog and scope, resolve and validate the pinned input schema, and check the trusted dispatch receipt. A null receipt is acceptable only for a currently verified non-effectful, unprotected operation. `admitDispatch` must verify the governing provider and its evidence against current authenticated authority state. Callback approval is not a wire field; never derive it from a client boolean or from the presence of an artifact reference. These callbacks do not replace the provider's durable serialization, one-use consumption or idempotency records.

The boundary checks invocation/input/operation identity before invoking either callback, fences completion after each await, and preserves canonical result discriminators. `outcome.status=succeeded` may contain a denied decision, an intermediate capability status, or an unknown effect. Only a confirmed capability `succeeded` payload contains output. Metadata validation checks the shape of schema and evidence references; the consuming resolver must still resolve authorized immutable bytes and validate the output against its original schema. It must never fetch a URL merely because it appears in a reference.

A local exception after entry to `invoke` or `authorizeDispatch` sets `ProviderBoundaryError.effectMayHaveStarted=true`. Preserve the original invocation and idempotency key for reconciliation. The boundary does not retry, claim rollback, issue grants or synthesize receipts. A thrown provider error has a safe local code without the provider's raw message.

Invalidation subscriptions use sequence zero for each new stream, including a resumed subscription; the request's prior sequence is a source cursor. The boundary enforces contiguous frame numbers, fixed identities, scoped data, an explicit terminal and EOF. It withholds the terminal until bounded EOF verification rejects extra frames. Data may already have been delivered when a subsequent frame fails, so a cache consumer must invalidate on stream error or an explicit gap and refresh before protected use. Consumer cancellation aborts the provider signal; an uncooperative iterator cleanup cannot delay return indefinitely.

This component does not certify durable idempotency, actual PWCE authority/action semantics, artifact-store contents, cold process recovery, selected-provider qualification, physical effects or Human acceptance. Those remain owner-specific integration obligations.

## Earlier coarse-grant admission path

The existing authenticated tool route now records the principal, Assistant, session, capability, input digest and checked dispatch binding in the same SQLite transaction as admission, one-use consumption and audit. The binding includes endpoint/environment labels, capability version and complete definition digest, provider route, snapshot identity/revision, interaction, authority context, execution mode and original deadline. A later request cannot supply missing identity for a historical admission. Exact retries return the recorded admission; changed identity conflicts. The evidence accessor returns the actual recorded bytes with their digest and size under an explicit trusted current-owner check. This is internal evidence of the checks performed, not a reconstructed canonical HumanAuthorityDecision.

Before provider I/O, the server durably claims that original admission once. Two database owners or processes cannot claim it twice. Claiming rechecks grant ownership, revision, scope, session, expiry, mode, deadline and the caller's current guard. A stored claim survives restart and missing provider output; further use remains unknown and requires reconciliation. Audit or storage failure rolls back the corresponding transaction. Existing one-use grants are not recreated when a claim fails.

These changes repair the existing runtime path but do not complete canonical consumer migration. The administration endpoint still uses its existing internal endpoint/environment labels and coarse capability grant terms. The HTTP request layer now binds a required UUID idempotency key to one invocation before provider work, preserves verified responses across restart, rejects changed content and revalidates access before replay. Incomplete records stay uncertain without replacement dispatch. The local administration status resource can now reconcile an original invocation under its durable provider/scope/schema binding, append observations separately, and preserve the original HTTP reply. Full canonical request envelopes, authoritative effect-evidence references and final scope mapping remain outstanding. Historical backup restore fencing, real PWCE admission and action reconciliation also require their separate integration evidence.

## Canonical grant storage

`CanonicalGrantRepository` stores the published `GrantRequest`, `HumanAuthorityGrant` and `GrantLifecycleEvent` records in separate SQLite tables. Creating a request is inert. Approval compares the current request revision, confirmation digest and explicitly confirmed class and deadlines, then commits the terminal request, exactly one grant, issuance event and command response together. Competing approvals and denial serialize on that same database transaction. Recorded command retries return the original result, including after revocation; they do not revive permission. Callers must read current grant state for current eligibility.

The host supplies a current authenticated principal, governing provider, clock and scope guard. A trusted capability adapter supplies scope derived from validated arguments, the input digest and deterministic effect summary. The repository checks these bindings and exact schema shapes; it does not authenticate a caller, resolve authentication-evidence bytes or derive scope from raw capability arguments itself. When an adapter can provide only an input-bound scope, reusable session and persistent grants are rejected.

Request history and grant events retain their original bytes and SHA-256 digests. Expiry is enforced directly and can be materialized lazily; terminal grants never reactivate. Approval fails if the clock is invalid, predates the request, or crosses a request/grant/review deadline during final ownership checks. Records with mismatched digests or IDs and inconsistent event histories are withheld. Storage is bounded to 4,096 requests and 16,384 command results; it fails explicitly at capacity instead of evicting retry or approval history.

`evaluateCanonicalGrant` is a non-consuming eligibility function for one explicitly selected grant. It checks current Human/session/provider context, normal execution mode, endpoint/environment/Assistant identity, exact capability version and operation, target/data subsets, one-use invocation and input bindings, lifecycle state, and expiry/review boundaries. Empty data scope means no data access. Its result is an eligibility disposition, not a canonical decision artifact or dispatch receipt.

The focused tests use temporary databases, a virtual clock, synthetic identities and independent competing database workers. The canonical HTTP API below adds owned listings and authenticated audit custody. The preparation composition described below now supplies scope from validated inputs for explicitly configured adapters. The canonical dispatch integration below supplies consumption and a real admission ledger. Control-web migration, full invalidation subscriptions and the PWCE capability adapter remain outstanding. Existing coarse grants retain their original storage; this migration does not assign them missing canonical terms. The saved administration service has not been restarted or migrated by this work.


## Canonical grant HTTP administration

The local-password server now handles the nine published `/api/authority/v1` grant routes with the canonical request and response schemas: list/get/create requests, approve/deny/cancel a request, list/get grants, and revoke a grant. The current control-web grant screens still use the earlier Assistant-scoped endpoints; switching that workflow remains separate work. The explicitly composed tool dispatcher below now uses canonical preparations and grants.

POST bodies are the published envelopes with request ID, correlation ID, idempotency key and typed payload. Path IDs must match payload IDs. GETs accept request/correlation ID headers and generate missing IDs. List queries use `assistantId`, comma-separated `states`, `limit` (default 50, maximum 100), and an opaque `cursor`. Unknown or duplicate query fields are rejected. Cursors bind the Human, Assistant, list/filter/limit and source revision; changing those or changing stored state requires a fresh page. Each page repeats current authentication and Assistant permission checks.

Canonical JSON decoding rejects invalid UTF-8, malformed JSON, duplicate keys including escaped spellings, more than 128 KiB, more than 8,192 structural/string tokens, or nesting beyond 32 levels. Contract validation rejects forged principal/state fields and invalid types. Cookie mutations retain the existing origin and CSRF checks. Direct grant creation, deletion, state replacement and AuthorityProvider.authorizeDispatch have no writable administration route. The protected tool route below constructs dispatch authority requests internally. Errors use the canonical failure envelope with safe codes; another Human's IDs are not disclosed.

Creating a new request requires the trusted `ServerOptions.canonicalAuthority` composition input. It supplies an environment UUID, a current-scope guard and an asynchronous proposal resolver. The resolver must retrieve the original invocation and derive its material scope and input digest from validated arguments under the selected capability contract. Returning client fields unchanged is not such verification. The API compares every submitted display/authorization term with the trusted proposal and checks the current session's actual logical endpoint, environment and Human ownership again before commit. Missing composition stays unavailable for new creation/approval; it never derives authority from the request body. PWCE governance never falls back to this local provider.

Approval captures a credential-free local authentication proof and commits it with the request decision, grant, lifecycle event, immutable record snapshot, audit record and idempotency response. The provider-owned audit format `urn:lifestream:local-authority-audit:1` records operation, request/correlation IDs, Human/Assistant, command digest, disposition/revision, reason, event IDs and a digest-bound reference to the exact resulting canonical request/grant snapshot. `urn:lifestream:local-authentication-proof:1` records verified identity/session/origin and authentication/verification times; it contains no cookie, token hash, CSRF value, password or MFA material. These are local evidence formats, not new authority transport envelopes. Artifact references resolve to actual owned SQLite bytes; replay verifies the audit, linked snapshot and approval proof before returning success. An audit-write failure rolls back the whole approval.

An identical command returns its original recorded result without consulting a changed proposal source or creating another grant. Current authentication, Assistant permission and evidence access are still required. The returned decision may precede a later revocation; clients must refetch the current grant to display current eligibility. A changed command under the same key conflicts. Historical command results without the required audit custody are not upgraded by fabricating references.

Canonical GETs do not change stored request/grant state or create lifecycle events. They return the stored lifecycle record; grant views separately compute eligibility against current time, session, endpoint, host scope and proof custody. The request's explicit `expiresAt` remains authoritative even while its stored state is pending. Review/expiry boundaries deny permission immediately without requiring cleanup. Grant histories are bounded by the current finite lifecycle, and grant detail reads now include actual admitted invocation IDs from the canonical dispatch ledger. Mutation replies preserve the IDs captured by the original serialized command; replay does not replace them with a later ledger view.

The original API validation uses real local-password HTTP sessions, temporary databases and a synthetic trusted proposal source. The preparation integration below replaces that test-only proposal map with a server-owned retained invocation when explicitly composed. It covers all nine schemas/routes, atomic audit rollback, stale/forged terms, idempotency after revocation, cross-Human isolation, pagination, scope withdrawal during resolution, strict JSON decoding, read-only expiry views, evidence corruption and external-governance refusal. It does not establish the actual deployment/capability proposal adapter, canonical control-web UX, final dispatch, selected-provider qualification, physical effects or Human acceptance. No saved service was restarted or configured.

## Authenticated canonical capability preparation

`ServerOptions.canonicalCapabilities` connects a selected canonical CapabilityProvider, environment UUID, immutable schema store and versioned semantic adapters to the real authenticated server. It is mutually exclusive with the old capability provider and separately supplied proposal resolver. Its provider reference must match the selected capability profile. PWCE governance rejects this local composition; it cannot obtain local grants as a substitute for PWCE authority. Changing the selected capability or authority provider fences retained and in-flight preparation; it cannot keep using the old composition. No saved profile or running service is changed by adding this composition support.

Use `POST /api/authority/v1/assistants/:assistantId/tools/:capabilityId/prepare` with the same local-password cookie, origin and CSRF header as other protected administration calls. The body contains only `idempotencyKey` (UUID), `capabilityVersion`, `input`, `requestedClass`, `grantExpiresAt`, `reviewAfter`, `expiresAt` and `untrustedRationale`. All fields are required; the nullable `reviewAfter` and `untrustedRationale` fields must be explicit. You cannot submit principal, endpoint, environment, invocation, scope, digest or effect-summary overrides. The server takes those identities from its current Human/session/logical endpoint and configured environment. The endpoint must have a known personal audience and healthy state. Replay/simulation preparation is not routed through the live local authority store.

Preparation reads the provider through `CanonicalProviderBoundary`, checks catalog membership/version and provider route, resolves the configured exact input/output schema artifacts under current scope, validates input and output-schema syntax in the bounded worker, then calls the configured semantic scope adapter. The adapter derives target/data references and an effect summary from the validated arguments. Its revision and exact schema artifact metadata are retained. An input-bound-only adapter cannot request a session or persistent grant. The requested preparation expiry must be in the future and no later than the retained snapshot expiry; grant and review deadlines are checked separately. No grant or provider invocation is created by preparation.

The response contains `preparation` (the trusted request terms and scope-derivation classification), `grantsAuthority:false` and `dispatchStarted:false`. To create a canonical approval request, use `preparation.request` as the source of the published CreateAuthorityRequest payload, omitting the server-only `environmentId` and `sideEffectClass` fields. Submit it in the existing canonical envelope to `/api/authority/v1/requests`. The resolver retrieves the original invocation from SQLite and compares the submitted fields with those retained terms. On fresh approval it rechecks the original snapshot, schema access, input and derived scope. The final serialized guards recheck current ownership, endpoint state and grant-state binding. The approval transaction excludes only its own grant issuance from that last comparison; another grant change still invalidates the preparation. Approval remains separate from dispatch.

Migration 32 retains the original invocation, validated input, input/output artifact references, catalog snapshot and capability definition, provider/adapter identity, owner binding, request terms and their digest. A separate persisted authority-context mapping advances when the authenticated owner/endpoint/grant binding changes. Both registries are bounded to 4,096 records and fail explicitly at capacity. Identical preparation retries return one retained invocation; changed content under the same key conflicts. Concurrent requests serialize the final insert. Storage failure cannot leave a usable partial preparation. Corrupt bytes, withdrawn access, expired preparation or a different provider snapshot prevent new approval requests. Restart preserves the record but still requires the provider to verify the same unexpired snapshot; a replacement catalog cannot silently stand in for the original.

The tests use the actual HTTP authentication, preparation and canonical approval routes with a synthetic canonical provider and schema registry. They cover exact material scope, duplicates/concurrency, forged fields, schema denial, audience withdrawal during a provider wait, expired/corrupt records, reusable-scope refusal, failed writes, provider switches and restart. Initial source-runner and missing-build failures and the corrected owner-normalization regression are retained in the local test logs. This is preparation/approval integration evidence. The canonical final dispatch integration below now consumes these preparations. The control-web workflow and actual PWCE capability/authority adapter remain open; the earlier coarse-grant tool-invoke route remains separate.


## Canonical final dispatch

An explicitly configured `canonicalCapabilities` composition supplies a canonical capability provider, immutable schema store, versioned scope adapters and a trusted governance adapter. Governance must return a current disposition with actual evidence bytes, expose a synchronous current-source check, and resolve result evidence under the same owner scope. Missing governance leaves dispatch unavailable. Browser/model fields never configure these adapters or supply authority context, material scope, arguments or receipts at dispatch.

After preparing and approving the request, invoke:

`POST /api/authority/v1/assistants/:assistantId/tools/invocations/:invocationId/dispatch`

The body contains only `grantId` and the original preparation `idempotencyKey`. The actual authenticated session, origin, CSRF and Assistant permissions protect the route. The dispatcher refreshes the catalog for the authority revision created by approval while preserving the original invocation, input, interaction, capability definition, schema artifacts, provider route, target/data scope and display terms. Endpoint/audience or provider selection changes fail closed. Historical preparations without the new host binding are not assigned missing terms. Expiry of the pending request alone does not revoke an already approved grant; current grant, call and snapshot deadlines govern admission.

The dispatcher constructs `AuthorityDispatchRequest`, checks the exact selected grant with non-consuming `evaluateCanonicalGrant`, and calls the repository's internal `authorizeDispatch`. One SQLite writer transaction checks the current grant revision, actual authentication proof, snapshot/current scope and provider disposition/evidence; appends the canonical `HumanAuthorityDecision` receipt and audit; records the invocation; and consumes `allowOnce`. The receipt records the checked pre-consumption grant revision. The grant and consumption event link the resulting decision ID. Any failure rolls back all these writes before a provider call is possible. Revocation uses the same serialization boundary: revocation first prevents admission; admission first remains admitted and is listed by grant inspection and revocation replies.

The provider boundary can start the initial call only after a separate unique durable claim validates the receipt custody and current host/provider scope. Identical dispatch retries read the original admission and result without claiming again. A crash between admission and claim, claim failure, interrupted call, invalid output or unavailable evidence preserves `outcomeUnknown`; a consumed grant is never refunded. Even an unclaimed admission is not automatically resumed on retry. This is at-most-one initial dispatch, not a claim of exactly-once physical effects.

`GET /api/authority/v1/assistants/:assistantId/tools/invocations/:invocationId` reads that original record under current authentication and ownership. A successful output requires the canonical provider result, original output-schema validation and digest/length-verified provider evidence, retained with the immutable first result. Intermediate or missing results remain uncertain. Releasing recorded output still requires current host ownership and access to the original output schema; withdrawn access withholds the reply while preserving the stored result. Reads and replays cannot dispatch or substitute another provider. The status reconciliation path below now queries the original canonical provider. Full authority invalidation subscriptions, control-web integration, PWCE mapping, backup-restore fencing and selected-provider/physical qualification remain separate work. The existing coarse-grant reconciliation path is not used as a fallback.

The added integration tests exercise real local-password HTTP authentication and SQLite, with only synthetic provider actions. They cover original input and receipt custody, concurrent retries, grant/revocation ordering, distinct invocation denial, missing/malformed replies, current audience/provider checks, missing governance, expired grants, historical incomplete preparation, corrupt evidence, audit/receipt/claim/result write failures, and restart. No saved Human service or live provider is changed by these tests.


## Recovering an uncertain canonical outcome

`POST /api/authority/v1/assistants/:assistantId/tools/invocations/:invocationId/reconcile` accepts an empty JSON object under the existing origin, cookie and CSRF checks. It uses the original admitted provider, invocation ID, idempotency key and complete scope to issue a bounded canonical `CapabilityProvider.getInvocation` request. It never obtains another catalog, evaluates or consumes a new grant, claims an invocation, or calls `invoke`. An admission without an initial-call claim remains uncertain without contacting the provider. Already confirmed outcomes are read from storage.

Current authentication, Assistant ownership, session/endpoint/audience binding, provider selection and access to the original output schema are required. Schema access is checked before contacting the provider and after the provider/evidence awaits. Original grant expiry or consumption is not interpreted as permission to retry an effect; status is a read of an already admitted operation. The current provider must enforce scoped read access. A different provider, scope, invocation, schema or receipt cannot substitute for the original. Confirmed output is validated against the original schema, and evidence bytes must match their owned reference's digest and length. Missing or invalid replies, cancelled/deadline-expired calls and failed persistence release no new confirmation.

Migration 34 stores bounded, append-only canonical status observations and their evidence separately from the immutable admission and initial result. The first confirmed success or failure remains terminal; a late concurrent uncertain reply cannot replace it. Sixteen uncertain observations are retained, with a seventeenth slot reserved for eventual confirmation. An additional uncertain reply returns a capacity error without pretending it was recorded. Read-only queries can still obtain a terminal reply for that reserved slot. Restart preserves the original response and all recorded observations, and no observation refunds a consumed grant or dispatches an effect.

The GET resource and reconciliation response distinguish current evidence from the original dispatch response: `status` reflects the latest retained observation, `originalStatus` and `result` retain the initial outcome, and `latestObservation`/`observationCount` identify the newer evidence. An identical POST to `/dispatch` continues to replay the original dispatch result. Reading stored provider details, including uncertainty reasons and failure messages, still requires current schema access; evidence stays stored when a reply is withheld. Provider queries are explicit through `/reconcile`; GET performs no provider status query or observation write.

The HTTP tests cover recovery without rediscovery or re-admission, restart, immutable initial results and observations, concurrent terminal/uncertain replies, output and receipt mismatches, missing/corrupt provider evidence, current access withdrawal before and during reads, failed observation writes, capacity with reserved confirmation, finite deadlines and no late writes. They use synthetic providers and temporary databases. This establishes the local canonical recovery path; PWCE mapping, effect retries, backup restore fencing and real physical qualification remain separate obligations.

The local external decision binds that observation to the original canonical invocation, input, scope and snapshot. Evidence reads require those original bindings, current host access, unexpired custody and a current read of the original producer snapshot. Records are bounded, process-local and expire no later than the original call deadline or catalog expiry. Reads never reevaluate or dispatch.

It confirms previews make zero target calls. Unit checks additionally cover changed inputs and scope, foreign-tuple qualification, local-grant rejection, malformed replies, approval restrictions, concurrency capacity, mutation during awaits, cancellation and deadlines. This component is not final admission, invocation or a complete AuthorityProvider. ## PWCE original invocation and status recovery

`PwceInvocation` now supplies canonical `invoke` and `getInvocation` operations against the original admitted producer action. It negotiates `pwce-action-invocation.bundle.v1@1.0.1`; `scripts/generate-pwce-invocation-pin.mjs` verifies the public producer manifest, ordered artifact bytes and exact admission, dispatch and capability dependencies. The proof embeds the unchanged original admission, the actual dispatch attempt and start time, the first dispatch result, the current result and any reconciliation reference. A response must agree with that proof and with the retained canonical input, scope, receipt, snapshot and producer action. Transport completion alone cannot become effect confirmation.

A new invocation requires current trusted host admission and the original current catalog. `SqlitePwceInvocationCustody` commits the original request and unique invocation/key binding in migration 37 before the first dispatch call. The wire request preserves the producer's original action, key and deadline. No automatic retry can acquire another claim. A lost reply, cancelled call or failed observation write leaves that claim available only for status lookup. A duplicate invocation uses the canonical status path, including after SQLite close/reopen; changing its input, correlation, key or scope cannot create a replacement action.

Status lookup uses the original action and foreign scope through the authenticated Agent Gateway. It requires current local/host ownership and current producer access, but it does not renew admission, extend the original dispatch deadline, require an unexpired discovery snapshot or send another effect. An unknown action, missing proof, revoked context or mismatched reply withholds output. It cannot fall back to an older successful observation. Catalog and authority-context restoration or rotation still require their own integration work.

The canonical status union has fewer variants than the producer result. Mapping preserves these distinctions in the retained proof:

| Producer observation | Canonical status |
| --- | --- |
| Admitted, with no dispatch attempt | `authorized` with the original receipt |
| Started | `started` with the original attempt's start time |
| Succeeded | `succeeded` with actual producer output, schema and confirmation evidence |
| Denied | `denied` with the producer reason category |
| Failed with known effect state, or a result explicitly reporting no external effect | `failed`, never retryable; effect state is `confirmedFailed` or `notStarted` |
| Partial success, timeout, cancellation or failure with unresolved effects | `outcomeUnknown`, with the original producer status in the reason and original action reconciliation reference |

Partial success is never projected as complete success. The immutable proof retains the complete producer result, including its original status and effect field, even when the canonical status must use the broader `outcomeUnknown` variant.

Observation history is separate from the original request. It retains at most 16 nonterminal observations plus a reserved final confirmation; exact duplicates consume no additional space. It does not evict original claims or historical proof. A confirmed terminal result cannot regress or change materially, and a recorded attempt, start time or first dispatch result cannot be substituted. Evidence reads first check current producer access, then revalidate the requested historical proof, original binding, exact artifact metadata, SHA-256 and UTF-8 length. Composite proof validation explicitly permits at most 131,072 bytes; ordinary capability values remain limited to 65,536 bytes and schemas to 16,384 bytes, with the same bounded worker execution.

The separate-process runner now checks actual invocation success, exact proof, SQLite reopen, duplicate status-only recovery, a discarded invocation response, foreign-session refusal and revocation. Its two canonical invocations and two existing raw-dispatch scenarios make exactly four synthetic target calls. Unit and storage checks cover corrupted or substituted evidence, write failures, competing database owners, bounded history, terminal regressions, expired admission, scope withdrawal and uncertain outcomes. This establishes the invocation/status component and process-restart behavior. Incomplete-admission recovery is described below. ## PWCE catalog invalidation custody

`PwceCapabilityCatalog.invalidateAuthority` is a trusted adapter/host ingress for a validated local authority-context reference. It drops every retained projection using that exact provider, context ID and revision, including projections for other sessions or traces under the same authority. Other authority contexts remain usable. `invalidateAll` drops all retained projections when continuity is unknown. Both return the removed local snapshot IDs for downstream invalidation; neither method accepts a foreign event as authentication or grants permission.

Catalog discovery registers its read before resolving the host binding. Snapshot revalidation and schema access also register their reads. Invalidation aborts affected calls, including calls waiting on a resolver or transport that ignores cancellation, and prevents late replies from returning or repopulating the catalog. Active reads are bounded by the configured catalog capacity. Completion, failure, cancellation and invalidation release their slots. A fresh read may legitimately return the same immutable producer snapshot; it cannot rescue an earlier invalidated call.

These methods preserve the original snapshot digest checks and any recorded substitution failure. They do not erase durable admission or invocation custody. Historical action reads still require current host ownership and actual PWCE proof; removal of catalog custody cannot renew dispatch permission. The canonical SSE mapping is implemented by the component below. Host subscription lifecycle and saved runtime activation remain separate integration work; these ingress methods alone do not establish an active subscription in the saved runtime.

## Canonical PWCE invalidation streams

`PwceInvalidationStreams.subscribeCapabilities` and `subscribeAuthority` implement the two canonical subscription methods. Supply the same trusted provider identity, binding resolver, current-owner check and `PwceCapabilityCatalog` used by the action adapter. Wrap the resulting provider methods with `CanonicalProviderBoundary`. The component is implemented and tested; the saved server has not been configured to use it, and complete PWCE host composition remains outstanding.

Each subscription owns all sites in its resolved binding. It first reads authenticated, scoped replay through the published Gateway, drains any replay pages, then opens SSE at each site's actual returned watermark. That handoff includes events accepted between the replay read and connection setup. The optional host `onReady(scope, signal)` callback fires once all site connections have authenticated, accepted SSE headers. The signal closes with that subscription; a host can use it when requesting fresh state. An attempt that never connects every site cannot report success. The default instance capacity is 256 physical site streams, enough for both canonical ports over a 128-site binding. Capacity failure is explicit and never silently drops a site.

Each site enforces its own producer cursor order. Filtered global cursor jumps are valid, and different site connections can deliver in different arrival orders. A repeated event within one subscription is suppressed while its identity is retained. Reusing an event ID or cursor with conflicting content fails the subscription. Parallel logical subscribers each receive the relevant notification. A new or resumed subscription may deliver an earlier event again with its original ID; the consumer must handle at-least-once delivery. Recent original event bytes remain available through `readEventEvidence` under the exact current host scope. These are bounded local receipts of data already received, not a new PWCE evidence fetch, a current authorization result or a durable audit ledger.

Canonical frame sequence starts at zero for every subscription and is contiguous in delivery order. Terminal `lastSequence` identifies the last canonical data frame (zero for an empty stream). It is **not** the PWCE resume cursor. A successful terminal's `sourceRevision.revision` and `sourceRevision.highWaterMark` both contain the lowest acknowledged producer cursor across the sites. Resume with `afterSequence = Number(sourceRevision.highWaterMark)` and the returned `sourceRevision`. Conflicting values are rejected. Using the lowest cursor preserves unseen events on a slower site; the original producer cursor and source revision are retained in each local event receipt.

An explicit replay gap produces a canonical `gap` notification, discards catalog state and starts future delivery at the producer's reported current watermark. It never restores a cached snapshot. Live resync controls, malformed or conflicting events, unexpected EOF, late data after a terminal, loss of authority and failed connections produce a failure terminal. Expired or withdrawn authority is rejected. Capability changes map to `catalogChanged`; authority changes map to `authorityChanged` on the capability port and `providerChanged` on the authority port. Provider degradation also requires reevaluation. Context and action notifications advance their validated source cursors without inventing grant or capability changes.

Every relevant notification invalidates the shared catalog before it waits for notification queue space. Opening or closing a subscription also invalidates its authority's catalog custody. Already-running catalog and schema reads are fenced by that invalidation. Output names the known PWCE light capability and carries no snapshot IDs from other sessions. A notification never authorizes or dispatches an action. Historical admission and invocation custody remain separate from current catalog permission.

The default queue holds 128 canonical data frames per subscription. Slow consumers apply backpressure while affected catalog state is already invalidated; each site retains at most its current bounded frame while waiting. The default watch lasts ten seconds, with a maximum of 25 seconds inside the request's maximum 30-second deadline. Normal rollover cancels transports, preserves only acknowledged cursors and releases physical capacity even if a consumer stops pulling. Cancellation, `return()`, current-owner withdrawal and deadlines also stop outstanding work, including a custom source that ignores cancellation. Raw event JSON is limited to 64 KiB, 32 levels and 8,192 structural/string tokens, and rejects duplicate keys. Recent identity checks and event evidence are bounded; they are not an unlimited deduplication history.

The focused regression suite covers both canonical boundaries, all 128 sites, parallel ports, replay pages and gaps, source ordering, duplicate identities, malformed input, actual transport readiness, queue backpressure, cancellation, rollover and ownership. The separate-process dispatch runner additionally opens both canonical streams against PWCE, refreshes their catalog after readiness, revokes producer authority, and verifies rejected stream completion plus immediate catalog removal. Full configured host lifecycle, external grant-query representation and saved runtime activation remain separate work.
