# Local authentication and scoped administration

Local authentication is an explicit instance option (`authority.authentication: local-password`), separate from inference/provider selection. Existing profiles remain unchanged. `scripts/start-isolated-auth.mjs` starts an opt-in loopback instance using an explicitly selected private data directory and installer-token file. It never imports personal data or restarts a provider. The default selected profile is synthetic `test`; another existing profile must be named explicitly.

```sh
LIFESTREAM_ISOLATED_DIRECTORY=/absolute/private/test-instance \
LIFESTREAM_INSTALLER_TOKEN_FILE=/absolute/private/installer-token \
LIFESTREAM_PROFILE=test node --experimental-strip-types scripts/start-isolated-auth.mjs
```

Create the installer-token file privately with at least 32 random bytes, set its mode to `0600`, and retain it outside Git and ordinary logs. It is consumed as enrollment authority, never a login credential. The installer claim closes permanently when the first Owner is enrolled. The recovery batch uses only synthetic accounts and an isolated directory; no existing live configuration is selected automatically.

The shared `/control/` application provides local setup, sign-in, optional MFA enrollment, recovery, profile administration and a link to `/control/security.html` for accounts, explicit Assistant permissions, grants, Skills and operation-bound proposal review. An Owner provisions additional accounts. New accounts have no Assistant administration scope or capability grants. Assignment of an Assistant administration permission does not permit reading another subject's relationship or delegate another Human's grants. Relationship content is checked against the authenticated subject separately.

Passwords use Node's maintained `crypto.scrypt`: N=32768, r=8, p=3, 32-byte verifier, independent 16-byte random salt, 64 MiB maximum workspace. Passwords contain at least 12 code points and at most 1024 UTF-8 bytes. At most two derivations run concurrently. Sign-in and recovery are limited per account (five attempts per 15 minutes) and remote address (40 per 15 minutes); successful sign-in resets only its account bucket. Parameter selection follows [OWASP password-storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Optional MFA uses offline [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) HMAC-SHA1, six digits, a 30-second period and a one-step clock window. Enrollment emits a standard `otpauth` URI and requires a valid current code. Normal login never falls back to password-only while MFA is enrolled. Accepted steps are fenced durably against replay; the seed is AES-256-GCM encrypted with principal-bound associated data. The implementation's RFC vectors and URI parameters are tested. Use of a particular physical authenticator application remains a Human review action, not an inferred brand-specific acceptance claim.

The setup ceremony supplies ten distinct 256-bit recovery codes. Recovery requires only the account name, one unused Owner code and a new password; neither lost original factor is required. It revokes all sessions, clears the lost MFA enrollment and returns one replacement recovery code. Other unused codes remain available, including if a response is interrupted. Authenticated Owner credential confirmation can rotate the whole set and revoke sessions. Raw passwords, codes and MFA values are never in account listings, diagnostics, model inputs, audit payloads or Git.

The `authentication-safety` directory is a distinct restore boundary from `application.sqlite`. It holds a private encryption key, encrypted credential-transition snapshots, epochs and replay/revocation fences. Credential intents are durable before application SQL changes; startup completes interrupted changes. Restoring an older application database re-applies the current credential snapshot, so consumed codes, revoked sessions and old passwords do not revive. Interrupted setup resumes into the original account: sign in with the selected password and, if delivery was interrupted, rotate recovery codes after credential confirmation. Never restore this safety directory from an older snapshot alongside the application database. Its destruction, total-machine rollback or compromise requires an explicit operator recovery procedure; the implementation does not claim rollback resistance after loss of its current independent safety state.

The browser cookie is HttpOnly and SameSite=Strict. This implementation serves loopback HTTP only and rejects non-loopback hosting, mismatched Host and cross-origin mutations. It does not claim public HTTPS deployment support. Mutations use a session-bound CSRF token, and imported/model-authored changes use an inert proposal and an explicit Human review bound to operation, target, content, expected revision and authentication session. Reauthentication cannot reuse an old proposal approval. No session or CSRF material is supplied to inference.

Administrative authority expires server-side exactly 1,800 seconds after the last successful Human administrative action. GET polling, health checks, background work and conversation traffic do not refresh it. Conversation authentication continues independently until logout, revocation or credential change; an expired administration session cannot approve or mutate. Signing out also works after the administrative idle deadline. These boundaries follow the selected policy and [OWASP session-management principles](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Capability requests and decisions reuse `authority_grants`, its event history and the existing admission repository. Terms explicitly select one-use, session or persistent duration with a bounded expiry. One-use dispatch consumes the grant atomically; current principal, Assistant scope, expiry and revocation are checked at admission. Skill drafts, schema validation, revision history and explicit activation reuse the existing Skill contract/current table. A Skill's activation is never a capability grant. Discovery and isolated simulation cannot dispatch effects. When this instance has no capability provider attached, the surface reports unavailable instead of fabricating tools or authority.

Capability discovery, invocation and status reads are asynchronous. The host supplies one bounded deadline, cancellation signal, execution mode and current-session check. If you sign out while discovery is pending, the result is unavailable and no tool list is released. A grant revoked or expired while a call is waiting cannot admit a new action. Local review and grant changes remain synchronous transactions; waiting for a provider does not hold a review transaction open.

A capability snapshot stays bound to its Assistant, endpoint, session, environment, authority and execution mode. Replay discovery cannot be reused for live invocation. Repeated concurrent requests with the same invocation identity share one attempt. A lost response after dispatch is shown as an unknown outcome and is not automatically dispatched again. Reconciliation belongs to the original provider; an HTTP success alone does not prove an effect. Skill steps await their outcomes and stop when an earlier step is uncertain.

To check this path using synthetic data, run `pnpm build`, then `node --test --experimental-strip-types packages/runtime/test/capabilities.test.ts packages/runtime/test/capability-schema.test.ts packages/runtime/test/capability-artifacts.test.ts packages/runtime/test/skills.test.ts apps/server/test/security-administration.test.ts`. The tests include temporary authenticated HTTP services, delayed providers, logout, invalidation, one-use grants and uncertain effects. They do not use the saved control-plane service.

Capability arguments are checked against the declared JSON Schema before consuming admission. Wrong types, out-of-range values, unexpected properties and malformed nested data are rejected without conversion or silent defaults. Schemas must compile locally; an unresolved schema reference does not authorize a network fetch. Failed refreshed discovery invalidates the earlier snapshot.

Successful output must match its original declared output schema before it is released. If an effect was sent but its response is invalid, the outcome remains unknown and is not retried automatically. A fresh resolver can recover a successful result when the original provider supplies its output-schema reference and a configured schema store still authorizes the exact bytes. This lookup does not discover new tools, consume approval or invoke the action again. If the reference or authorized bytes are missing, the result is withheld. No output contract is guessed from the returned value.

Referenced schemas use the existing ArtifactRef fields: reference, SHA-256, media type, schema identity and byte length. A schema URL is an identifier, not permission to fetch it. The configured store verifies and copies its pins, checks access on every read, and allows at most 256 schema records. The runtime verifies returned bytes again before parsing them. Missing stores, changed digests or lengths, unresolved references and disagreement with the discovered schema stay unavailable; they never fall back to a broader inline schema. The authenticated administration server accepts this store only through its trusted construction options.

Schema checking runs in a bounded worker, so expensive validation cannot freeze the conversation thread. Each check has a two-second limit within the existing overall request deadline; cancellation ends validation. The current limits are 16 KiB per inline schema, 64 KiB per input/result, 32 nesting levels and 8,192 JSON nodes. The worker has a 64 MiB heap limit and keeps at most 128 compiled schemas; it does not retain arguments after each check.

Local software checks, synthetic tools, rendered browser interaction, real inference, physical devices, Human acceptance and production readiness remain distinct evidence classes. No local-auth test claims Human acceptance or a production release.


## Retrying a tool request

`POST /api/authority/v1/assistants/{assistantId}/tools/{capabilityId}/invoke` requires a UUID `idempotencyKey` in the JSON body alongside `input` and an optional `grantId`. Create the key once for an intentional invocation and preserve it when retrying that request. Unknown body fields are rejected. Do not generate a new key merely because the response was lost or timed out. A new key means a new intentional invocation.

The server records one invocation and interaction identity before provider discovery or dispatch. An identical retry returns the original verified response and request/correlation IDs. Different input, grant, capability, Assistant, session or execution mode under the same key yields a conflict. Authentication and current Assistant permission are required for every replay; another Human's key is not a readable record. Stored successful output must still validate against its pinned schema through the currently authorized schema store. Missing or revoked schema access withholds the result without invoking again. Inline-only legacy results without a recoverable schema reference cannot be released as verified cold replays.

If the original request is unfinished or its result could not be persisted, a retry returns HTTP 202 with the original invocation and an `outcomeUnknown` result. The original call may still finish, but the retry never dispatches it again. A stored HTTP failure is also replayed as the original failure. Status reconciliation must use the original invocation; this endpoint does not silently create a replacement. Replaying a result does not invalidate conversation context as though another effect had occurred.

The local request ledger retains at most 4,096 identities and bounds each recorded response to 128 KiB. It returns HTTP 429 when full, preserving existing identities instead of evicting them and allowing duplicate effects. Request input is represented by a digest; verified response data is stored separately from the authority audit and remains subject to current read checks. This is the existing local tool route's retry contract, not completion of the entire canonical runtime API or PWCE action protocol.


## Inspect an uncertain tool invocation

`GET /api/authority/v1/assistants/{assistantId}/tools/invocations/{invocationId}` checks the original invocation. Use the invocation ID returned by the original tool request and the same authenticated Human/session with current Assistant administration permission. This read does not need a new grant, idempotency key, or input body. It never discovers tools, consumes a grant, invokes an action, or invalidates conversation state.

A confirmed success returns 200 and validated output. Intermediate or unknown provider status returns 202; a confirmed denied/failed status returns 403. A missing or differently owned invocation returns 404. If the provider, current scope, schema access, deadline, or evidence storage cannot be verified, the response is 503 without output. These codes describe this local administration projection; it is not the full canonical provider envelope.

The trusted server composition must supply `capabilityProviderIdentity` alongside `capabilityProvider` and `capabilitySchemas` to enable provider recovery for new requests. The identity names the configured provider installation/outcome store; it is not accepted from HTTP input. Keep it stable only while the same original invocation store remains authoritative. Do not derive it from a display label or reuse it for a replacement provider. Before invoking, the server durably binds that identity, the actual capability/version/route, execution mode, owner scope, and original output-schema reference. Historical requests without this binding cannot be rebound through current discovery. A provider with no original outcome returns uncertainty; server restart does not imply provider outcome persistence.

Recovered observations are stored separately with sequence, observation time, and exact response-byte digest. Repeated identical observations occupy one entry. Up to 64 changing nonterminal observations are retained, with a reserved final confirmation entry; capacity failure preserves prior evidence. A late unknown result cannot overwrite a confirmed result. Reads recheck current permission and schema access, including after restart. The original POST always retains its original reply; use this status resource for later confirmation. A missing original HTTP reply can also be recovered without rewriting that missing response. No live service is automatically configured for this feature.

## Current identity revalidation

Contexts issued by the local authentication adapter are immutable. Before a protected read or mutation, the adapter resolves the stored session from its private token hash and verifies the same Human, session ID, origin, authentication time and Owner flag against current account/session records. Assistant permissions remain a separate current check. A copied context with changed identity cannot list Owner accounts, create grants, refresh administration activity, create Assistant permissions or revoke another session. Creator permission assignment itself requires a current Owner.

The trusted clock must be finite and valid and cannot precede the recorded authentication or latest administration activity. Those checks apply to conversation authentication too, without imposing the administration idle limit on conversations. Context expiry metadata cannot extend the server's stored idle deadline. An unchanged context can still be revalidated after legitimate activity refresh or adapter reopening; logout remains available after administration idle expiry while conversation authentication is current.

These are backend checks demonstrated with synthetic local accounts and temporary databases, including the existing grant-administration path. The tests do not establish a remotely exploitable HTTP attack: the public request path already derives context from the cookie. They close the internal context boundary needed for canonical authority integration. Canonical grant API/UI and dispatch migration remain separate unfinished work.
